## Finding

Read again on 2026-10-16 from the primary sources below. **Two kinds of hook.** Session hooks fire only inside a session the user started, never on a repository event: Claude Code's `SessionStart`, `PreToolUse`, `Stop`, and the rest (<https://code.claude.com/docs/en/hooks>; `SessionStart` stdout becomes the agent's context), Codex's `.codex/hooks.json` or `[hooks]` in `config.toml` (<https://developers.openai.com/codex/hooks>; `SessionStart` stdout becomes developer context), Cursor's `.cursor/hooks.json` (<https://cursor.com/docs/agent/hooks>; `sessionStart` returns `additional_context`, is fire-and-forget, and does not run in Cursor cloud agents), and the Amp plugin's `session.start`, which aayudha's plugin turns into a notice to the user, not agent context. Repository event triggers start an agent on a GitHub event. **Amp** (<https://ampcode.com/docs/github>, and `create_github_subscription`'s own schema): orb spawners only for a newly opened issue or PR, each with an optional label (`issue_label`, `pr_label`), for one repository or every repository of a personal installation (`installation_id`); "comments and CI updates cannot be used to spawn new orbs"; comment (`issue-comments`, `pr-comments`, which also reports the merge) and CI subscriptions (`ci`: `workflow_run`, `check_run`, or `status`) need one issue, PR, or exact commit and continue an existing thread; a spawned thread is subscribed to its source's comments and reviews, not to pushes; a spawner keeps saved `instructions`. Live finding: a `pr_label` spawner fired for PR #252, whose label `gh pr create --label` added just after creation, although the docs say the label must be present at open. **Cursor** (<https://cursor.com/docs/cloud-agent/automations>, <https://cursor.com/help/ai-features/automations>, changelog <https://cursor.com/changelog/06-18-26>): Draft opened, PR opened, PR pushed, PR merged, Push to branch, PR commented; on GitHub also PR and issue label changed, CI completed, Workflow run completed, Issue comment, PR review comment, PR review submitted, Review thread updated; PR approved is GitLab and Bitbucket only; Webhook (an HTTP POST with the automation's key); no issue-opened and no release trigger; runs as Me or a service account. The `cursor/cursor` Terraform provider v0.8.0 (`terraform providers schema -json`) expresses `cron`, `git_pull_request` (`pr_action` opened, pushed, merged, commented; `ignore_draft_prs`, `comment_contains`), `git_push`, `git_ci_completed` (`condition` failure, success, any; `branch`, `ignore_base_failures`), `git_label` (issues or pull requests, `on_added`, `on_removed`, `label_name`), and `webhook`; draft opened, workflow run completed, issue comment, PR review comment, review submitted, and review thread updated are web-app only. **Claude Code**: routines' GitHub triggers are still Pull request (opened, closed, labeled, synchronize, …) and Release only, with no issue, check, or comment event (<https://code.claude.com/docs/en/routines>); auto-fix answers CI failures and review comments on one PR a person turns it on for (`/autofix-pr`; <https://code.claude.com/docs/en/claude-code-on-the-web>); Code Review reviews PRs on open or push, Team and Enterprise only (<https://code.claude.com/docs/en/code-review>); `@claude` on GitHub runs claude-code-action in Actions with an API key (<https://code.claude.com/docs/en/github-actions>). **Codex**: scheduled tasks run on a schedule and, on ChatGPT web and mobile for eligible plans, "from supported app events", which the docs do not enumerate and do not name GitHub; they are created in the app or by asking ChatGPT, with no API or CLI (<https://learn.chatgpt.com/docs/automations>); Team Tasks take event triggers through the team's app connections, Business and Enterprise only, as the team's service account, with Gmail and Slack as the examples (<https://learn.chatgpt.com/codex/enterprise/teams>, `help.openai.com/articles/20001540`); the GitHub app reviews PRs automatically on PR events, and a person's `@codex review` or `@codex <task>` on an issue or PR starts a cloud task as that person (<https://learn.chatgpt.com/docs/third-party/github>). **GitHub**: a `check_suite` created by Actions starts no workflow

## Implemented instead

The matrix, default-loop events (native = the host starts the run; chained; session = the user's next session; mention = a person posts it): issue opened (`triage-new`, label `intake`): Amp native spawner, Cursor native `git_label` (the form adds the label), Claude session, Codex session or a person's `@codex`; Feedback filed (`feedback`, label `type:feedback`): the same; PR opened or updated (no default loop): Amp native for opened, session for updated, Cursor native `git_pull_request`, Claude native routine, Codex session, review only by its app; CI failed (`ci-failed`): Amp **chained**, Cursor native `git_ci_completed` (`failure`), Claude session plus per-PR auto-fix, Codex session or a person's `@codex`; release published (`release-measure`): Amp session, Cursor session, Claude native routine, Codex session. Rendered: Amp's `ci-failed` is now `loops/amp/ci-failed.json`, a `pr-opened` spawner whose instructions subscribe the new thread to the PR head's CI (`ci`, this-thread), re-subscribe when a later event shows the head moved, and run the loop on a failure; it covers each PR's opening head and any head the thread sees, not a push made after the last event it received, and it starts one Amp thread per new PR. Cursor's provider pin is `~> 0.8`. Where a host has no trigger, the rendered file says so plainly ("Picked up by your next session") and `aayu hook session-start`, already each host's session-start hook, lists the events: for each event loop no host runs with its current digest in `loops/active.json`, it reads GitHub as the user (5-second limit, read-only, numbers and tags only, no untrusted titles), since the cursor in `.aayudha/state/loop-events.json` (first session: 24 hours), and prints each loop's events with its steps, which start with the halt and budget guard; the agent offers them to the person. Nothing runs between sessions. Codex and Claude also name what a person can do (`@codex <task>`, auto-fix), never posted by a workflow (no `allowed_bots`, D-4.5b.7); `@claude` is not installed, because it needs an API key in CI.
