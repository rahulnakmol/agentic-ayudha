# D2

## Plan assumption

WP0.1 solo mode: the founder approves their own protected-path PR on a commit other than the last push

## Live result

**Not enforceable.** GitHub refuses self-approval (`Review Can not approve your own pull request`). A ruleset with `require_code_owner_review: true` and 0 required approvals did not block a `skills/` PR authored by the sole code owner (scratch PR #2 merged, rule-suite `result: pass`). Requiring ≥ 1 approval would block every PR to `dev`, not only protected paths, and turn every merge into a bypass

## Implemented instead

Workflow `protected-paths` (`pull_request_target`, so GitHub runs the default branch's copy and a PR cannot weaken it; it never checks out PR code) fails when a PR changes any path in the base branch's `.github/CODEOWNERS`. Ruleset `protected-paths-codeowner-review` requires that check (and keeps native CODEOWNER review switched on for when approvals become ≥ 1); its only bypass is the repository admin role in `pull_request` mode. A protected-path PR therefore merges only through an explicit admin bypass, which GitHub records in the rule-suite history with `result: bypass`; the hand-run reconciliation lists these until `audit` automates it (WP7.6). Because the workflow must be on the default branch, the gate covers `dev` from the PR after PR1; PR1 itself, which creates it, merged on green CI. WP1.4 extends the gate to pass on an approving review of the head SHA by a human CODEOWNER who is not the author (bot-authored PRs); WP5.1 switches to native CODEOWNER review with ≥ 1 approval when a second human seat is added. CODEOWNERS also covers `.agents/` and `.claude/` (host execution surfaces) and the whole of `.aayudha/config.toml`, because CODEOWNERS cannot protect the `[models]`/`[autonomy]` sections alone
