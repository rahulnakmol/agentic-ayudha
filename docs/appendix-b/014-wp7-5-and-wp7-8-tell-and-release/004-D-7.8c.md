# D-7.8c

## Plan assumption

WP7.8: `release` is a human's act, run at a terminal with a confirmation (identity human, TTY gate); agents are refused

## Finding

The founder's policy (AGENTS.md, "Promotion and release (no human approval)") is that agents promote on their own once the gate is green, and the founder asked for it ("i totally support it and we should build it", Story #430). After #192 recognises every host's agent markers, `release` would refuse every agent, so the policy could only be followed by hand. Agents have no terminal, so a TTY gate cannot be the control; the gate is

## Implemented instead

`release` no longer refuses agents or asks them to confirm: the full `ci.yml` gate (gate=rolling with `evals-gate`, or gate=stable) still decides, with the same merge-commit names, tags, and `release.yml`. CI and bot accounts are still refused. A person at a terminal is still asked (or passes `--yes`). `--to main` needs the explicit stable-release request (gate `stable-request`): a person's yes at a terminal, or a comment on the Release issue whose first line is `Stable release: vX.Y.Z`, written after the rolling snapshot by a non-bot account with write, maintain, or admin access, with no `<!-- aayudha:` marker; the promotion record names its author and URL. aayu never writes such a comment, and the pre-tool hook (Claude Code, Codex, Cursor) denies an agent's `gh`/`curl`/`wget`/`http`/`xh` command that carries one. Limit: in solo mode the agent holds the person's token, so GitHub cannot tell who typed the comment; the request is enforced by aayu and the hook, not by authentication, until agents write as a bot identity (Level 3), where a bot's comment never counts. `release` is now model-invocable and exposed over MCP as a write (`expose_writes`). `decide --accept` and the `ship`/`plan` `--solo-bypass` stay human-only. Tests: `TestReleaseLadder`, `TestPreToolBlocksHumanOnlyShell`
