# D-7.5a

## Plan assumption

WP7.5: `tell docs\|guide\|changelog\|release\|launch\|brand`; tone from `brand.yaml`; claims link only to Features with authoritative packs; UTM tagging; `tell publish` human-identity only, logged; accept: a guide references only proven Features, publish refuses a bot identity

## Finding

`tell` runs in the host (mode `host`), so the host's model writes the copy and the binary can only brief and check it. Packs belong to stories, not Features, and the plan does not say what makes a Feature proven, what counts as a claim, which links get which UTM values, or where publishing puts the copy: the docs site is WP8.2 and no blog or social integration exists. `grill brand` (WP5.3, #101) was built in parallel

## Implemented instead

`internal/tell` plus `internal/cli/tell.go`. New registry inputs: `--from` (the host's Markdown draft), `--tag`, and `--campaign`. Without `--from`, `tell <kind>` prints the brief: the voice, tone, and avoided words, the Features that may be claimed, and the UTM tags. A Feature is proven when at least one story or bug under it (at any depth) is done (merged, released, measured, done) and every done one is covered by an authoritative pack: one that maps every Ready criterion, matches its hashes, and whose floors hold. This is the `status` proof-coverage rule (WP2.8), so coverage must be k/k with k > 0. Outside a checkout the ledger cannot be read, so nothing is proven. Tone: `design/brand.yaml`, read with grill brand's own strict parser (`design.ParseBrand`); tell uses `name` and `voice: {tone, avoid}` and leaves the palette and pairs to grill. A missing file, tone, or avoid list falls back to the documented default: a plain, specific, calm voice and an avoid list of hype words (`seamless`, `revolutionary`, `best-in-class`, …). Single or hyphenated words on the avoid list are refused literally; longer entries ("exclamation marks") only guide the host. With `--from`, every link to an issue or pull request of the repository is a claim: `#N`, `owner/name#N`, or any `issues/N` or `pull/N` path (absolute, root-relative, or relative, as GitHub resolves them) that does not name another repository on github.com. Each must be a proven Feature, so stories, bugs, PRs, and unproven Features are refused. Avoided words are refused too, case-insensitively, outside URLs. Any refusal exits 4 and lists the problems by line. Fenced code blocks, delimited as CommonMark renders them (closed only by a run of the opening character at least as long), are neither checked nor tagged. Every other absolute http(s) link gets `utm_source=<repository name>`, `utm_medium=<kind>`, and `utm_campaign=<--campaign, else --tag, else <kind>-<date>>`; a link that already has a `utm_` parameter keeps the author's. The checked copy is written to `.aayudha/tell/<kind>/<campaign>.md`. `--publish` (human-only; never exposed over MCP) is refused, with exit 4 and no writes (not even the local copy), for an agent lane (`AAYU_AGENT=1`), in CI (`--ci`), and when `GET /user` for the human token reports a bot (`type: Bot`, a `[bot]` login, or `[identity] bot_logins`). A human's publish is one `tell.publish` action in the log. It lands `tell/<kind>/<campaign>.md` and a `.json` publication record (SHA-256, cited Features, UTM, who, and when) on the ledger. For `release` with `--tag`, it also replaces tell's `<!-- aayudha:tell -->` block in that tag's GitHub Release notes; a tag without a GitHub Release, such as `rolling-*`, is left alone. `tell.ReleaseNotes` writes deterministic notes for `release` (WP7.8): shipped stories grouped under their proven Feature, linking only the Feature, with the rest counted and not described. Tests: `TestTellGuideCitesOnlyProvenFeatures` and `TestTellPublishHumanOnly` (the thin slice shipped end to end against the fake GitHub and a local ledger), `TestLoadBrand`, `TestTag`, `TestCheckFences`, `TestCheckRefs`, and `TestReleaseNotes`
