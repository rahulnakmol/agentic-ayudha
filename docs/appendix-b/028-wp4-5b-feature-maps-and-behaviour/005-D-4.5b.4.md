# D-4.5b.4

## Plan assumption

WP4.5b.4: `verify --maintain` posts the brief on one tracking issue with an @-mention of `[verify] maintainer`; the loops hand off

## Finding

GitHub notifies a mention only in a new comment, not an edit. The apps answer only the people who connected them (the same finding as the merge-gate thread's reviewer apps): Codex and Cursor ignore a bot's mention, and claude-code-action ignores bots unless `allowed_bots` names them. Amp has no @-mention. A nightly hand-off of unchanged drift would ask for the same PR every night

## Implemented instead

`internal/cli/verifymaintain.go`, `internal/verify/maintain.go`. Each hand-off is a new comment on the issue whose body carries `<!-- aayudha:verify-maintain -->` (opened once, titled "Keep the feature maps honest"); the comment carries the report's digest, and `drift` mode posts nothing when the last brief has the same digest. Outside CI the brief is posted under the person's account; in Actions it is posted as the bot App, which records the hand-off but does not reliably wake an app, so the loop's Amp or Cursor schedule, which runs as the person, is the dependable path. `[verify] maintainer` is `claude`, `codex`, `cursor`, or `amp` with no default (schema only, no CONSTRAINTS.md row); unset or `amp`, the brief has no mention and the Amp loop thread follows it. Loops `verify-sweep` (02:30 daily, `verify --check all --maintain drift`) and `verify-maintain` (Mondays 09:00, `verify --map --maintain always`), both `bot = true`; a loop's new `setup` (pinned `node`, `pnpm`) and `setup_run` give the Actions job the product's browser tooling. The sweep's job is red when a check fails. Test: `TestVerifyMaintainHandoff`
