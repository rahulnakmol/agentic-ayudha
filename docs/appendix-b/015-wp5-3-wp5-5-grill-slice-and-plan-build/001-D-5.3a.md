# D-5.3a

## Plan assumption

WP5.3: question sets per type in `references/<type>.md`; baseline required before a target on Goal/Initiative; refuses Ready without a validator pass; writes via `actions` under the human's identity when a human runs it, the bot otherwise; `grill brand` → `design/brand.yaml` with an AA palette check; bubbletea TUI for the CLI, prompt for MCP/skill; untrusted wrapping of pasted material; accept: ten tier-1 fixtures end in an issue passing `ready` 10/10, tier 2 on `grill goal` and `grill story` meets the WP3.4 bar with the results committed as the baseline, a Goal with no reachable baseline is refused Ready naming the metric

## Finding

Feedback and Incident are intake: `ready` refuses them by design (WP2.7, WP2.9), so no Feedback or Incident issue can pass `ready`. The plan names no brand file format, no AA thresholds per use, no baseline window, and no rule for metrics no adapter serves (WP7.2's snapshot metrics). bubbletea v2.0.10 and later need Go 1.26 (D5). CI cannot push a results file to `dev` (D-3.4a). Two more tier-2 cases do not fit the 12 USD cap

## Implemented instead

`grill <type>` takes all ten types plus `brand` (new enum value). A human run writes with the human token, untagged; an agent lane (`AAYU_AGENT=1`, MCP) writes under the bot, or the tagged human fallback (WP1.4). New issues carry `type:<type>` and `status:planned`, or `status:backlog` for intake, as the forms file them. Goal and Initiative: a Metric `<source>:<metric> [filter]` (the `measure` syntax) is fetched through its WP5.2 adapter over the 28 whole UTC days before today and written into the Baseline section (value first, then metric, population, half-open window, fetch time, and the source query in a fence), replacing what the draft held; when the adapter is missing, unreachable, or write-scoped the draft fails Ready (exit 4, nothing written) with `baseline: no reachable baseline for metric "<metric>" (a Target needs a reproducible baseline first): <adapter error naming [integrations.<name>]>`. A snapshot metric (`activation`, …) must already hold its measured value in Baseline, else the same refusal. Without `--title`/`--body`, a human on a terminal gets the bubbletea TUI (`charm.land/bubbletea/v2` v2.0.9): one question per field in schema order with the reference's questions as hints, parent and labels last, a review screen running the same validation that jumps to the first problem and creates only a passing draft; pasted text only becomes answer text. MCP: the `grill` prompt serves every reference and takes an optional `material` argument, wrapped as `<untrusted source="pasted">`. `grill brand --body <yaml>` parses `design/brand.yaml` strictly (`version`, `name`, `voice {tone, avoid}`, `palette {name: "#rrggbb"}`, `pairs [{fg, bg, use}]`) and checks every pair's WCAG contrast, floored to two decimals, against 4.5:1 for `text` and 3:1 for `large-text` and `ui` (SC 1.4.3, 1.4.11); any failing pair or missing text pair refuses (exit 4, nothing written); `--create` writes the file in the checkout for a PR. Tier 1: `evals/cases/grill/<type>-…` for all ten types record `grill <type> … --create`, then `ready 21 --check` for the eight non-intake types; for Feedback and Incident the run ends at the created issue, and the case's Ready check is the schema validation of the recorded item (`TestTier1GrillEveryType`). Tier 2: `grill/story-empty-claims` and `grill/goal-first-claim` carry rubrics and send their question set through `[tier2] references` (WP7.3's key); `max_usd` is 15.0. The results of the first passing `evals.yml` run on `dev` are committed as `evals/results/<sha>.json` in the next PR
