# D-5.4f

## Plan assumption

D-5.4d: the case's scope rules remove negated forms first, so a plan that promises the opposite is not floored

## Finding

The skills group failed twice in a row on `plan/config-migration`, mean 4.2 and 4.0 but pass^5 0 against the v0.2.0 baseline (1.0): push run [39013697227](https://github.com/rahulnakmol/agentic-ayudha/actions/runs/39013697227) on fb84b73 scored 5 5 5 5 1, and push run [39014607367](https://github.com/rahulnakmol/agentic-ayudha/actions/runs/39014607367) on 233c3df scored 5 4 5 5 1. Both 1s were the same floor, the case's `downgrade` scope rule, on plans that rule a downgrade out: "no downgrade path other than restoring the backup" and "No data is dropped, and no downgrade transform or re-serialisation is used". Story #41's criterion 2 is a rollback that restores the file byte for byte, so both plans honour it. D-5.4d gave the `reject legacy` rule an allow phrase for negated forms but left the `downgrade` rule without one. So the case's rule was wrong, not the skill and not a regression: the plan skill and the case had not changed since D-5.4d, and the runs in between passed (42bab33: 5 5 5 4 4)

## Implemented instead

The `downgrade` rule gets the same negation allowance as `reject legacy`: "no", "not", "never", "without", or "n't" up to two words before "downgrade" removes the match first. A plan that adds a downgrade ("a downgrade collapses the per-kind values back into one scalar") is still floored. `TestPlanScope` keeps both sides with the two recorded phrasings. Confirmed with a filtered run of just this case on dev after the merge (a dispatch on the PR branch cannot reach the tier-2 jobs); its result is recorded in D-3.4i
