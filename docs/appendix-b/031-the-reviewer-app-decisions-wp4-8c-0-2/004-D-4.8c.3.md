# D-4.8c.3

## Plan assumption

S-4.8c: the reply turns into the gate's verdict

## Finding

A comment or review cannot be a `pull_request_target` event, and a status set by a comment-triggered job could be set by any job

## Implemented instead

Triggers `issue_comment` (created, edited) and `pull_request_review` (submitted, edited) start only the `reply` job (`actions: write`, read access, default-branch checkout, no secret; a review event runs the PR's copy of the file, which can only ask). It runs `aayudha inspect "$PR" --ci`: with a reply for the head from the chosen reviewer, it waits for the head's `pull_request_target` run and, when `aayudha/merge-gate` passed and `aayudha/inspect` failed, calls rerun-failed-jobs, so the base-copy run's inspect check carries the verdict. The `gate`, `inspect`, and `pack` jobs run only on `pull_request_target`; the concurrency group splits gate and reply. This repository's own gate failed on #225 only because it installs dev's binary, which did not know `[inspect] apps` yet
