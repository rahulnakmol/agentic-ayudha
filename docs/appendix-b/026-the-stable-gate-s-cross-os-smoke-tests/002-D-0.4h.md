# D-0.4h

## Plan assumption

D-0.4f: with the `live-tests` token, the stable gate's `extended-integration` job runs every live test green

## Finding

Run 38754333645 on `dev` failed two live tests that pass from a workstation with the same classic token; re-running only that job passed both, so neither was the CI credential. `TestLive` (internal/github) counted on GitHub's default labels for a second page of five, and a new repository sometimes has none yet. `TestReleaseLive`'s `release --to main` landed `main`, then GitHub refused the `v0.1.0` tag push with a bare `[remote rejected] v0.1.0 -> v0.1.0 (failed)`. The "Bypassed rule violations … creations being restricted" lines above it are GitHub's notice that the admin role's bypass was used, not the refusal. `(failed)` carries no reason; it is the answer GitHub gives for a lost race on a ref, which the ledger writer already retries (D-2.4a), and the re-run's tag push succeeded, so it was transient. This repository's `release-tags` ruleset matches the test's (creation, update, deletion, non-fast-forward; bypass: the admin role, always), and the founder's token reports `current_user_can_bypass: always`, so v0.1.0's tag push is admitted the same way

## Implemented instead

`TestLive` creates six labels, more than a page without defaults (`testdata/smoke.json` re-recorded). Every `release` push (candidate, landing, tag, candidate deletion; each idempotent) is retried up to three times, a poll interval apart, when the remote answers `(failed)` or `cannot lock ref`; any other refusal fails at once as before. `TestReleaseRetriesALockedRef`: a pre-receive hook leaves the tag's ref locked for the first push only, and `release --to rolling` still lands and tags
