# D-4.2b.a

## Plan assumption

S-4.2b: ship verifies that the artifact came from the merge-gate run on the exact head

## Finding

The workflow-runs API gives a run's `path`, `event`, `head_sha`, `head_branch`, and conclusion, but nothing that binds it to the pull request's base branch: `pull_requests` lists the open pull requests whose head matches (PR 3 into `dev` on the scratch run 38762241501) and is empty once they close (run 38752748439 of this repository), so a second PR from the same head into another base would appear there too. Artifacts cannot be attached to a run from outside it; only the run's own jobs upload them

## Implemented instead

`gatePack` (`internal/cli/ship.go`) lists runs of `aayudha-merge-gate.yml` for the PR's head branch, newest first, and accepts the first with path `.github/workflows/aayudha-merge-gate.yml`, event `pull_request_target` (so the workflow file is the base branch's, never the PR's), `head_sha` = the PR head, and `completed/success`, whose `aayudha-pack` artifact is unexpired, unzips without escaping paths, verifies every hash, and is for this story, PR, and head. A refusal (exit 4) names every run it passed over and why. `aayudha/pack` joins ship's required checks. Residuals, in the threat model (T4): the base-branch copy is trusted, so a change to the gate itself must land through review first; PR code runs inside the gate job (sandboxed, D-4.8a) before the upload
