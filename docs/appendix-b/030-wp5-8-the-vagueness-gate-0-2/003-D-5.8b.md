# D-5.8b

## Plan assumption

S-5.8: motion, abbreviations, rough ideas, and product thinking that derives a Goal and checkpoints; product-type-aware qualifiers

## Finding

Products differ: a web app's "fast" is interaction latency, a CLI's is startup and per-command p95. The binary cannot see what a request is for, only the checkout. A work item had no field for checkpoints

## Implemented instead

`internal/grill` detects product types from the checkout (`product:web` from page routes or a UI dependency, `api` from API routes, a net/http server, a web framework app, or an OpenAPI document, `cli` from a Go `package main`, a package.json `bin`, or an argument parser, `library` from a package or module manifest with no app, server, or command entry point; each fact names its evidence) and reports CLI `command:` facts (Go flag sets, cobra, commander, argparse) and web `motion:` facts (CSS and inline `transition` and `animation` durations, motion libraries such as framer-motion), with `gap:motion` (no house durations to keep to) and `gap:reduced-motion` (motion without a `prefers-reduced-motion` rule). A catalogue dimension may name `Products:`; the assessment lists only the dimensions for the detected types (all of them when none is found), and reports tokens, motion, the a11y floor, and the performance budget only for web. New catalogues `vague/motion.md` (purpose, duration and easing budget, reduced motion, where it applies, how to prove it: a recording or a metric) and `vague/idea.md` (who, job, outcome, smallest provable slice, out of scope), and `references/jargon.md` (abbreviations with their meanings, and a Plain list such as API, URL, and CLI that never stops the gate); `ux`, `perf`, and `simple` gain CLI, API, and library dimensions (`perf.startup`, `perf.endpoint`, `perf.library`, `ux.cli-output`, …) and the qualifiers slick, sleek, nice, elegant, and stunning. A grilled Story or Bug (one with Provenance) now needs `Term: "<abbr>" → <meaning>; "<the human's words>"` (or `→ deferred:`) for each abbreviation of the request, and a **Checkpoints** section (new optional schema field, so the issue forms regenerate): `N. <what the human can see> (criteria 1, 2)`, numbered in order, every criterion reached by one. The readback (`grill.Readback`, the TUI's review screen and `grill --json`'s `readback`) states the Goal, "Measured by", "Done when", the checkpoints, and the terms. The plan skill orders its checkpoints to reach the story's, and build tells the human when one is reached. Bodies without Provenance are unchanged, so Ready already granted is not withdrawn
