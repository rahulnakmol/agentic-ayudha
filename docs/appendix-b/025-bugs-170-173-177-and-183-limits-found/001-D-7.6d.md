# D-7.6d

## Plan assumption

WP7.6 accept: re-running audit with the same recorded inputs produces a byte-identical report; WP1.9: files an earlier binary wrote stay readable

## Finding

Bug #183: the inputs snapshot recorded `config_hash` over the whole effective configuration, and `--replay` refused any difference, so every new key ([team] in WP5.1b, [ui] in WP1.1b) made every earlier report unreplayable (exit 4), though audit reads none of them. A whole-configuration hash cannot be recomputed by a binary with another configuration schema

## Implemented instead

New reports record `audit-config:sha256:<…>`, the hash of only what `audit` and `retro` read: `[identity] bot_logins`, `[decisions] sla_hours`, `[time]`, `[autonomy] correction_days`, `never`, `streak`, `[proof] media`, `media_secret`, `retention_days`, `[budget] per_story_usd`, and the dev branch; a replay refuses (exit 4) when that differs. A legacy `sha256:` hash is not recomputed: the replay renders the recorded hash, warns on stderr that it replays with the current values of those sections, and the byte comparison with the report is the check. Tested by `TestAuditReplaysRecordedReports` (the 12 October 06:35 and 15 October 04:35 UTC reports replay byte-identically from `internal/cli/testdata/audit-replay`: this repository's ledger up to the 15 October report as a 300 kB git bundle, with the config and `LAYERS.md` the replay reads) and `TestAuditRerunByteIdentical` (a `[ui] theme` change leaves the replay byte-identical; a `[decisions] sla_hours` change refuses it). A key audit starts reading must join `auditConfigHash`
