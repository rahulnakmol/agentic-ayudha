# D-5.7b

## Plan assumption

WP5.7 and D-5.7a: `aayu halt` sets a repository variable every workflow checks; every job in every aayudha workflow starts with the halt step

## Finding

Bug #173: `floors.yml`, `inspect-live.yml`, and `screen-reader.yml` had no halt step, and neither had the merge gate's `aayudha/inspect` and `aayudha/pack` jobs (in this repository and in the `init --gates` template), which D-5.7a counted as covered; nothing checked the rule, so a new workflow could drop it unnoticed

## Implemented instead

Those six jobs (and the template's two) start with the same halt step as the rest. `TestEveryWorkflowJobStartsWithHaltCheck` (repository root, run by CI's `build` job) parses every `.github/workflows/*.yml` and `internal/initrepo/*.yml` and fails naming each workflow and job whose first step is not the halt check (name `Halt check…`, `if: vars.AAYUDHA_HALT != ''`, a script that exits), then runs each halt script in bash with the variable set and requires a failing exit and the halt message. It covers `.yaml` files too. Live: on 2026-10-15 the three workflows from this branch ran on a scratch repository (`rahulnakmol/aayu-scratch-halt-1792045632`, created and deleted with the admin token, since the default token cannot create repositories): with `AAYUDHA_HALT` set every job (floors-web, floors-dast, inspect-live, both screen-reader readers) failed at the halt check and skipped every later step; after it was deleted the halt check was skipped and every job succeeded. The jobs API records are in `testdata/workflow-halt`, and `TestHaltedWorkflowRuns` checks them against the current workflows (inspect's first review asked for this evidence)
