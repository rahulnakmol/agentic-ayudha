# D-8.1b

## Plan assumption

WP4.5 and WP8.1: the merge gate runs every floor of a story on the PR head, the web floors against `[verify] seed` data; a product repository installs Playwright, axe-core, and Lighthouse itself (packages/floors)

## Finding

aayudha's merge gate installed only the Go-side floor tools, so a UI story's `a11y` and `perf` floors could only be blocked there. `examples/benefits-qa` lives in aayudha's own checkout, so its verify settings are aayudha's `.aayudha/config.toml`, and nothing starts the app in the gate. `[verify] seed` runs with the network and outside verify's PID namespace

## Implemented instead

aayudha's own `aayudha-merge-gate.yml` (not the `init` template, which leaves these tools to each product) checks out the base branch (never the PR's lockfile), installs `@aayudha/floors` with the frozen lockfile and denied install scripts, installs Chromium, and sets `NODE_PATH`, which verify already reads. `.aayudha/config.toml` gains `[verify] seed = ["examples/benefits-qa/deploy/serve.sh"]` (the script builds the example and starts it detached on seeded, synthetic data, then waits for `/healthz`), the local target `http://127.0.0.1:8787`, the example's Lighthouse budgets (`min_score` 0.9, LCP 2500 ms, CLS 0.1, TBT 200 ms), and `[measure]` events for its Goal (`benefits_visit` acquires, `answer_grounded` within 7 days activates). Only stories with screenshot or recording criteria run the web floors, so aayudha's own stories are unaffected. The layer table maps the example's directories (`web` L01, `api` and `cmd` L02, `ask` L03, `policy` L04, `answer` L05, `contracts` L06, `store` L07, `analytics` L08, `deploy` L09), which `go generate` renders into LAYERS.md and the seat charters
