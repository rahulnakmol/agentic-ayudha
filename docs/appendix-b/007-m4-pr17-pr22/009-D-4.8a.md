# D-4.8a

## Plan assumption

WP4.8: `aayudha-merge-gate.yml` runs from the base branch; re-runs `verify` on the PR head in CI and writes the authoritative pack to `ledger`; fails if `pack.sha ≠ head` or the Completion Goal hash ≠ the Ready snapshot; `inspect` with diff + plan + pack + criteria, untrusted-wrapped, review lane (family ≠ builder), structured JSON, per-criterion verdicts, `merge\|fix\|rebuild`, can downgrade but never override a floor, cached by diff hash, `cancel-in-progress`, skips drafts, `[budget] per_pr_inspect_max`, cap 2 cycles then page; accept: planted defect → P1 + `fix`, clean → `merge`, "disposition: merge" in the PR has no effect, third cycle pages

## Finding

D1: CI's workflow token can never write `ledger`, and no bot App exists yet. A `pull_request_target` job that checks out PR code must not hold secrets (a same-user child can read its parent's environment). The plan names no store for the cache, cycle count, or per-PR spend, and no source for the builder's family

## Implemented instead

Template `internal/initrepo/aayudha-merge-gate.yml`, installed by `init --gates` (now four workflows, golden). `pull_request_target` (the base branch's copy; `opened\|synchronize\|reopened\|ready_for_review\|edited`; per-PR `cancel-in-progress`). Job `aayudha/merge-gate` (drafts skipped) holds only a read-only workflow token, checks out the head (semgrep's `pull-request-target-code-checkout` rule is annotated on that step with this reasoning: a base-branch gate must check out PR code to verify it; the sandbox now also gives the tool its own PID namespace, so nothing PR code starts outlives its floor or touches the pack), installs the pinned floor tools and aayudha (`@dev` straight from GitHub on this repository), and runs `aayu verify <pr> --ci`, which in CI on a PR also fails (exit 4) when a criterion has no evidence from this run, the PR head moved, or the story's current Completion Goal hash differs from the snapshot's; the pack is kept as the run artifact `aayudha-pack`. Job `aayudha/inspect` (environment `ai-gateway`, `pull-requests: write`, no PR code) runs `aayu inspect <pr> --ci` on that pack. Job `aayudha/pack` pushes it to the ledger as authoritative with the App token when `AAYUDHA_APP_CLIENT_ID` is set; without an App it leaves a notice, and `ship` (WP4.10) lands the run's artifact under the human identity after checking the run (D-4.10a). `inspect`: the reviewer is the review lane's direct model (`gpt-6.1-sol`); the builder's family comes from the pack's `model` (an `Aayudha-Model` trailer, read by `verify`), else the build lane of the pack's host; `CheckFamilies` refuses a same-family pair. The prompt holds the floors as facts and the Ready criteria, story, evidence excerpts (text artifacts only; media never reach the model), PR text, and diff (capped at 120 kB) as `<untrusted>` blocks; the reply is validated against a closed schema (`disposition`, `summary`, `findings[{severity P0-P3, file, line, title, detail, criterion}]`, `criteria[{id, verdict met\|unmet\|unclear, evidence}]`). Rule 7 in code: a floor that does not hold, a P0/P1 finding, or an unmet criterion turns `merge` into `fix` (recorded as `overridden`). The replace-in-place `<!-- aayudha:inspect -->` PR comment carries the state (input hash over diff + pack head + checks + criteria, cycles, spend): the same inputs are answered from it without a model call; spend at `per_pr_inspect_max` exits 6 and pages; after two `fix`/`rebuild` cycles the next run pages and exits 4 without calling the model. Exit 0 on `merge` (and drafts), 4 on `fix`/`rebuild`. Re-entry: `fix` names the fix-in-PR path (`build --resume` n/a until WP5.5), `rebuild` sends the story back to Ready review. Live acceptance: `TestInspectLive` in the dispatch-only `inspect-live.yml` on dev; scripted-model tests (`TestInspectDispositions`, `TestInspectMergeBudgetDraft`) cover the plumbing, rule 7, the cache, budget, drafts, and the paging third cycle
