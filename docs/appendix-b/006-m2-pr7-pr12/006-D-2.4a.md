# D-2.4a

## Plan assumption

WP2.4: temp worktree, fetch-rebase-retry with bounded backoff, per-repo file lock, content-addressed paths

## Finding

GitHub reports a lost race between two pushes to the same ref as `[remote rejected] (failed)`, not as a non-fast-forward. A ledger commit is a set of whole-file writes and appends, so "rebase" can re-apply them to the new tip instead of replaying a patch. `flock` is not portable to Windows

## Implemented instead

`internal/ledger.Writer` fetches the tip into a private ref, builds the commit in a temporary detached worktree, and pushes it without force; on a rejected or lost-race push it waits (100 ms·2ⁿ with jitter, capped at 5 s, 10 attempts), resets the worktree to the new tip, re-applies the same files, and pushes again. A commit that changes nothing is not pushed. The lock is an `O_EXCL` file in the clone's git common dir, taken over after 10 minutes (a dead holder). `ContentPath` gives content-addressed paths. A token travels as an `http.extraHeader` in `GIT_CONFIG_*` environment variables, never on a command line; a human-fallback write carries an `Aayudha-Identity: identity:human-fallback` trailer. Each write is a `ledger.push` action, except checkpoint segment pushes (`ledger.Sink`, now the actions log's segment sink in a checkout, falling back to the local outbox when the remote has no ledger), which carry the log itself. Accept: 5 writers in separate clones plus 5 sharing one clone all land against a local bare remote (11 commits, every writer's commit an ancestor of the tip, shared appends intact), and 5 concurrent writers land on a live scratch repository (`TestLiveConcurrentWriters`)
