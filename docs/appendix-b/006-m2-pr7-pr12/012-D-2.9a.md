# D-2.9a

## Plan assumption

WP2.9: Incident → linked Bug; label-only enforced in `internal/actions`; the triage workflow is the only one that mints an `issues: write`-only token

## Finding

Creating the linked Bug is an issue write, which the labels-only capability forbids by design. The plan does not say how intake issues are recognised or how the binary decides when no host model did

## Implemented instead

Intake issues carry the `intake` label (the Feedback and Incident forms set it); triage refuses any other issue (exit 4, no writes). The class comes from `--as feedback\|bug\|incident` when the host's model chose it, else from the chore lane's model through the WP1.6 gateway, with the title and body in one `<untrusted source="issue">` block (a closing tag inside is escaped) and the answer validated against a closed JSON Schema (`class`, `accepted`, `reason`; anything else is rejected and asked again). Triage writes labels only, each write carrying the `labels-only` capability that the GitHub client checks per request: it adds `type:<class>`, `needs:grill` for accepted Feedback (grill creating the Feature is n/a until WP5.3), and the new label `needs:bug` for an Incident (`respond` files the linked Bug, WP5.6), and removes `intake` and any other `type:` label. `init --gates` now installs a third workflow, `aayudha-triage.yml` (golden): on `issues: opened/labeled` with `intake`, it mints a bot App token with `permission-issues: write` only when the App exists, otherwise uses the workflow token limited to `issues: write` by `permissions`, and runs `aayudha triage <n> --ci`
