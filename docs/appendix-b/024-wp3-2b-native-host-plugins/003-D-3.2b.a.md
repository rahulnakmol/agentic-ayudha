# D-3.2b.a

## Plan assumption

WP3.2b: Codex runs aayudha's plugin and project hooks, so `pre-tool` refuses a human-only verb there

## Finding

Megaman defect D-5.5c.12 (4) (PR #269, squash 68b65fa): Codex 0.162.1 skipped the hooks until the person trusted them in `/hooks`, so an agent ran `aayu ship 5`. Codex records trust per hook in the user's `config.toml` as `[hooks.state."<key>"] trusted_hash`. The key is `<plugin id>:<hook file>:<event>:<group>:<handler>` for a plugin and `<absolute file>:…` for a project; the hash is SHA-256 over the sorted, compact JSON of the event, the matcher, and the handler with Codex's defaults (developers.openai.com/codex/hooks; codex-rs `hooks/src/engine/discovery.rs` at rust-v0.162.0). Checked in this orb: aayudha's own hashes for the plugin's and an installed repository's hooks equal the `currentHash` that `codex app-server` `hooks/list` reported for all four, and `doctor` agreed with its `trusted`, `untrusted`, and `modified` verdicts

## Implemented instead

A `codex-hooks` doctor row (`hosts.CodexHookTrust`) reads that trust for the enabled plugin's hooks and the repository's `.codex/hooks.json`, and for an untrusted project. It fails, without blocking, naming each hook to trust in `/hooks`, including after a plugin update changes a hook. `install --host codex` says to trust the hooks; `docs/guide/hosts/codex.md` and `hosts/README.md` explain the step. `ship` gains no agent check here (PR #192). Test: `TestCodexHookTrust`, with the hashes Codex reported, and the doctor golden. Codex's normalisation is internal, so a later Codex may hash differently; `doctor` would then report "changed since it was trusted" until the person trusts again
