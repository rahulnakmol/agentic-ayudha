# D-3.2b.p

## Plan assumption

WP3.3: the aayudha MCP server in Cursor finds the GitHub token

## Finding

Megaman D-5.5c.23 defect (3): `status` through MCP said "no GitHub token" although `aayu` in Cursor's shell had one; the cause was unverified. **Verified here** with cursor-agent 2026.10.16-e3cb207: a stdio server that dumps its environment got only `HOME`, `LOGNAME`, `PATH`, `PWD`, `SHELL`, `TERM`, and `USER`; `GH_TOKEN`, `AAYU_GITHUB_TOKEN`, and `XDG_CONFIG_HOME` set in Cursor's environment did not reach it. The CLI builds the server's environment from `mcp.json` `env` only, merged over the MCP SDK's default list (`{...getDefaultEnvironment(), ...env}` in its bundle). So a token from `AAYU_GITHUB_TOKEN`, or a gh login that `GH_TOKEN`, `GH_CONFIG_DIR`, or `XDG_CONFIG_HOME` points at (megaman's ran with `XDG_CONFIG_HOME=/home/aicoder/.config` and a throwaway `HOME`), cannot reach it; the same explains the MCP doctor's "cursor-agent not signed in". `${env:NAME}` in `mcp.json` is not a fix: an unset variable reached the server as the literal `${env:NAME}`, and a changed value voided the server's approval

## Implemented instead

The server already tries `gh auth token` and aayu's secrets store, which need only `HOME`. doctor's `mcp` row, when Cursor is installed, resolves the token as the server would, from Cursor's variables only (gh and the secrets store included), and warns when this shell finds one and that does not, naming the shell's source and the fix: `gh auth login` with gh's default config folder, or `aayu auth set-secret github-token`. The MCP server's own no-token error now says that a host may start it without the shell's environment and what to use. Not covered: a keychain the server cannot reach without the session bus variables is seen by doctor as reachable. Tests: `TestCursorMCPToken`
