# D-3.2b.h

## Plan assumption

WP3.2b, D-3.2b.d, D-3.2b.f: committed files must not depend on one machine's plugin setting

## Finding

Founder follow-up (2026-10-17) to PR #279, its open point (3): #276 and #279 made `install` skip hooks, MCP and skill copies when the plugin was enabled on the installing machine (`lock.toml` `plugin_hosts`), so a teammate who cloned without the plugin got no skills. Checked in this orb. Claude Code 2.1.300: settings precedence is local > project > user (code.claude.com/docs/en/settings), and a committed `.claude/settings.json` `{"enabledPlugins":{"aayudha@aayudha":false}}` made `claude plugin list` show the user-installed plugin "✘ disabled"; `skillOverrides` does not reach plugin skills. Codex 0.162.1: a trusted project's `.codex/config.toml` `[plugins."aayudha@aayudha"] enabled = false` removed the plugin's skills from `codex debug prompt-input`, and `codex mcp list` showed no aayudha server; an untrusted project ignores `.codex/` but still loads `.agents/skills/` (probe skill). Cursor: plugin enablement lives with the account or its cache, with no committed per-project switch (cursor.com/docs/plugins)

## Implemented instead

Supersedes the machine-dependent parts of D-3.2b.d and D-3.2b.f: `plugin_hosts` is gone, and `install` writes the same files with or without the plugin. The committed copies are the source, and the plugin steps aside through committed project settings: `enabledPlugins["aayudha@aayudha"] = false` in `.claude/settings.json`, and `[plugins."aayudha@aayudha"] enabled = false` in the aayudha block of `.codex/config.toml` (a note instead when the product already has that table). The plugin's own commands (`/aayudha:next`, hand-offs) are off in such a repository. `hosts.PluginEnabled` now follows each host's precedence (Claude Code local > project > user; Codex a trusted project over the user layer). Not possible: Cursor has no committed switch, so its plugin and `install` together double; `install` says so. Codex: until the person trusts the project, it lists both copies; doctor reports it. Also fixed: a plugin hook stood aside in an untrusted Codex project, where Codex runs no repository hooks, so nothing refused a human-only verb; `hosts.RepoHooksRun` now requires trust. Tests: `TestInstallIsTheSameWithOrWithoutThePlugin`, `TestPluginHooksAndStatusLine` (untrusted vs trusted Codex)
