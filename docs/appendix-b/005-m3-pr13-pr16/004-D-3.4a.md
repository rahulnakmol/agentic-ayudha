# D-3.4a

## Plan assumption

WP3.4: tier 1 per PR (artifacts, schemas, produced issue passes `ready`, every `aayu` call succeeds, injection fixtures write nothing); tier 2 nightly and on promotion with a pinned judge from another family, k = 5, pass^k ≥ 0.8 and mean ≥ 3.5, a drop > 0.3 or any pass^k below baseline fails, baseline `evals/results/<main-sha>.json`, `[budget]` cap, skipped on fork PRs; first evals on `ready` and a stub skill

## Finding

The body-to-item parser and the `ready` verb are WP2.7, in the parallel M2 stack. `ready` is a deterministic verb (mode `none`), so there is no model reasoning for a rubric to judge. Live calls need the `ai-gateway` environment, which only dev, rolling, and main may use, so a `promote/…` candidate branch cannot run tier 2, and CI cannot push results files to `dev`. With n = k the unbiased pass^k estimator is 1 when all k runs pass, else 0

## Implemented instead

`internal/evals` plus `evals/` data (`eval.toml`, `schemas/workitem.json`, cases under `cases/<skill>/<name>/`). Tier 1 runs inside `go test` (`TestTier1`, CI job `build`) over recorded runs: artifacts exist; artifacts validate against JSON Schemas (the WP1.6 validator); work items, stored as `workitems.Item` JSON until WP2.7 parses issue bodies, pass `workitems.Validate` at Ready; recorded calls replay in-process (`AAYU_AGENT=1`) against a fake GitHub serving the case's `github/` fixtures, and a call to a verb without a handler is "n/a" (rule 1a), so `ready 12 --check` turns into a real check when WP2.7 lands; an injection case fails if any recorded call is a write or never-exposed verb, if the fake GitHub receives a write, or if the actions log records a performed action. Cases: `ready/story-ready` (tier 1 only, since `ready` has no model reasoning), `stub/csv-export` (tier 1 and 2), `stub/injection` (tier 1). The stub skill lives in `evals/skills/stub/` because `skills/` holds only registry verbs. Tier 2: the skill model is the case lane's direct model (`chore` on Claude Code: `claude-haiku-5-5`); the judge is pinned in `eval.toml` (`gpt-6.1-sol`, openai) and routed as a `review`-lane override; `models.CheckFamilies` refuses a same-family judge before any call. A run whose output is not a valid work item or fails Ready scores 1 without asking the judge (rule 7); otherwise the judge's 1-5 score passes at 4. Per case pass^k is 1 when all 5 runs pass; the suite's is the mean over cases. Inputs and outputs reach models in `<untrusted>` blocks. Spend: the gateway's `[budget]` breaker (story `evals`) and `max_usd = 1.5` per run, charged at the fallback rate when the gateway reports no cost; output is capped at 2000 tokens per call. `evals.yml` runs tier 2 in `environment: ai-gateway` nightly on dev, on pushes to dev that touch skills or the harness, on every push to rolling and main, and on dispatch, never on pull requests (so never on forks), and skips green while the secret is absent. Results go to `evals/results/<sha>.json`, uploaded as the artifact `eval-results-<sha>` (90-day retention) rather than committed; the baseline is a committed `evals/results/<main-sha>.json` if present, else the artifact of main's commit (a release can commit it by PR to keep it past 90 days). Promotion: the new `ci.yml` job `evals-gate` (rolling and stable gates) needs no secret: it fetches the results for the promoted commit (the candidate merge's second parent) and for main and runs `eval -compare`; missing results fail the gate with the dispatch command, and CONTRIBUTING's rolling procedure dispatches `evals.yml` on dev first. `internal/evals/**` joins layer L05
