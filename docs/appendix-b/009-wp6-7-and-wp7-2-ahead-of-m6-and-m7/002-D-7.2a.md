# D-7.2a

## Plan assumption

WP7.2: `measure` extends the WP5.2 adapters with GrowthBook, billing CSV, and App Insights/AWS/GCP exports; SQLite (`modernc.org/sqlite`) snapshots, DuckDB optional shell-out; AARRR/North Star queries; Results on Goal/Initiative; triggers the parent-close rule; accept: fixture exports → expected cohorts

## Finding

Built ahead of M7 (founder scheduling, 2026-10-12) with no billing, Azure, AWS, GCP, or GrowthBook account. The plan names no export formats, no AARRR definitions, no metric syntax for a Goal, and no home for snapshots. `modernc.org/sqlite` v1.60 requires Go 1.26 (D5). DuckDB is cgo (R7). WP2.8 says Initiatives and Goals close "on measure against baseline" without saying when a measure closes them

## Implemented instead

Exports are files, read by `internal/integrations/exports` as untrusted input (§0.1): `--billing` a CSV with a header (`user_id`/`Customer ID`, `created`/`Created date (UTC)`, `amount`, `currency`, optional `status`, only `paid`/`succeeded` counted, and `amount refunded`, netted), `--appinsights` Application Insights events as JSON lines (Log Analytics export `TimeGenerated`/`Name`/`UserAuthenticatedId` else `UserId`, or classic `timestamp`/`name`/`user_Id`), `--aws` CloudWatch RUM events (`event_timestamp` ms, `event_type`, `user_details.userId`), `--gcp` the GA4/Firebase BigQuery export (`event_timestamp` µs, `event_name`, `user_id` else `user_pseudo_id`). Rows become fixed, bounded fields (ids ≤ 256 bytes, names ≤ 200, no control characters, amounts with at most two decimals into minor units, a 1 GiB file cap); an unparsable row is counted as skipped, an unpaid one as excluded, and a file with no usable row is refused (exit 2). Sources are joined on the exported user id. GrowthBook joins the provider catalog as a baseline source (`growthbook:conversion_rate <tracking key> <metric ID>`, the control variation's rate in the latest results, windowed by GrowthBook's own analysis dates). `modernc.org/sqlite` v1.59.0 (the newest on Go 1.25) builds the snapshot at `.aayudha/state/measure/<issue or all>-<UTC time>.sqlite` (git-ignored; the Result records its SHA-256 and every export's, so it can be rebuilt; pushing snapshots to `ledger` is left for later) with tables `events`, `payments`, `sources`, and `meta`, keeping rows in the half-open window (`--from`, `--to`, default the 28 days before today). New config `[measure] acquisition activation activation_days retention referral north_star`. AARRR per weekly acquisition cohort, all bounds half-open: acquired at the first acquisition event in the window (any event when unset); activated by the activation event within `activation_days` (default 7); retained by activity (the retention event, or any) in days 7–13; referred by a referral event after acquisition; paying by a payment after acquisition, with revenue. A cohort is complete when its last user is observable for the whole horizon (`max(activation_days, 14)` days) inside the window. North Star: distinct users who sent the configured event, or `revenue` (the paid total). One plain-SQL query per question, run by the built-in engine or, with `--engine duckdb`, by the `duckdb` binary found on `PATH` (attaching the snapshot through its sqlite extension, with only `PATH` and `HOME` in its environment); both give the same rows, and doctor lists `duckdb` among optional tools. `measure <goal or initiative>` reads the metric from `--metric` or the Metric field: `acquisition` (users acquired), `activation`, `retention`, `referral`, `revenue` (rates over complete cohorts only; none complete is exit 4), `north_star`, or `<source>:<metric> [filter]` for a provider baseline over the window. The baseline is the first number in Baseline (none is the baseline gate, exit 4); the target is Target's optional comparator and first number (without one, the direction it lies from the baseline); a trailing `%` divides by 100. It sets `status:done` when the target is met, else `status:measured`, then writes the Result (verdict first, `Target met:` or `Target not met:`, then value, baseline, target, change, window, snapshot, sources, and the query), then applies the parent-close rule to the item and everything under it. `status` computes that rule for Goals and Initiatives too: every child released, measured, done, or cancelled, and a Result that starts `Target met:`, so `status --apply` also closes them. The fixtures are synthetic (`internal/measure/testdata/README.md`); the expected cohorts are worked out by hand in `TestMeasureCohortsAndResults`, and `TestMeasureDuckDB` compares DuckDB's answer when the binary is installed (it passed locally against DuckDB v1.5.6; CI skips it). Binary size grows from 21.6 to 25.7 MB (linux/amd64), under the 60 MB budget
