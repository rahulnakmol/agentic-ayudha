# D-5.9n

## Plan assumption

The founder's answer to the D-5.9l and D-5.9m checkpoints: the survey eval's self-check returns corrections only (a verdict for every item, whole-item replacements keyed by id, fixed keys for the fields without an id), applied deterministically and all or nothing, with the floors run again on the result and the first draft stored; tier-2 budget in stages; survey filing tests on the scratch repository `rahulnakmol/aayu-survey-scratch` with a token limited to it

## Finding

In run 39046436016 the self-check was 5.41 of the case's 14.11 USD, 3.25 of it a full redraft of 25k to 33k tokens per run. The redraft also reworded most items (70 to 82 of them per run changed by the id diff), so the scored draft mixed intended corrections with drift, and the first draft was not kept to tell them apart. No live test filed a survey backlog; the pilots' filing used the admin token by hand

## Implemented instead

**Corrections only.** The self-check prompt (`internal/evals/survey.go`) asks for one JSON object: a `verdicts` entry for every item that has an `id` (a backlog item's `key`): `keep`, `replace` with the whole item and the same id, or `remove`; `add` for a new item in a list named by its key path (`risks`, `modernisation.steps`, `items`); and `fields` for text without an id by key path (`summary`, `modernisation.strategy`, `open_questions`), never `request` or `product`. `applyCorrections` (`internal/evals/corrections.go`) checks everything first (an unknown or repeated id, an item without a verdict, a replacement that changes its id, an add with a used id, an unknown field, a field that would hold items) and refuses the whole reply with every reason, or applies it in an order that cannot fail. Items are the outermost objects with an id; what is inside an item is the item's own. The corrected draft keeps the draft's key order and its numbers as written. The floors run on the result; a reply that does not apply, or a result that fails them, gets one revision that asks for the corrections object again, then scores 1. `self_check.first_draft` and `self_check.corrections` reproduce the scored draft exactly, and `self_check.changed` lists only what the corrections changed (`E3 replaced`, `E5 removed`, `R1 added`, `summary set`). Zero-model fixtures cover each refusal and the order, numbers, and escaping (`TestApplyCorrections`, `TestApplyCorrectionsRefuses`), and the run's wiring, including a removal that leaves a step resting on the removed claim, is in `TestTier2SurveyRevisesOnceThenJudges`. Prompt caching waits for the gateway's answer on `cache_control`. **Budget stages:** stage 1 is `survey/tinyjs-rust` alone for about 15 USD or less, so the survey group's `max_usd` is 14 (a call can add about 1.1 USD after the check); stage 2, the other failing cases, only if stage 1 reaches 4.0; stage 3, the two consecutive full runs, only once every case has reached 4.0 in a filtered run; each stage raises the breaker in its own PR, and a breaker trip is a checkpoint. **Filing:** `TestSurveyBacklogCreateLive` (`internal/cli/survey_test.go`) files a backlog into `rahulnakmol/aayu-survey-scratch` under a product of its own per run, checks that a re-run files only what is missing and a third files nothing, then closes what it filed and deletes its label. It reads `AAYU_SURVEY_SCRATCH_TOKEN` (the `extended-integration` job passes it from the `live-tests` environment) and skips with that reason while it is unset; it runs outside a checkout, so the actions log stays local and the token needs only Issues read and write (and the Metadata read every fine-grained token has), not Contents
