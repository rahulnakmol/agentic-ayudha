# D-5.9d

## Plan assumption

Decision #287: modernisation stories prove behavioural parity with the legacy system, for example characterisation tests or golden outputs captured from the legacy build and run against the new one

## Finding

The binary cannot build every stack's legacy program, and a model must not decide whether two outputs match. A golden output captured in the caller's environment would also capture whatever that environment holds, tokens included, and vary by who ran it

## Implemented instead

`aayu survey --golden cases.json --bin <legacy program> --run` runs each case (an argv with `{bin}`, an optional stdin file and working directory inside the checkout, a timeout, and which streams it compares: stdout, stderr, exit) and writes `<id>.stdout`, `<id>.stderr`, and `manifest.json` (the program's SHA-256, the surveyed commit, each case's exit code and stream digests) under `<out>/golden/<cases file name>`, so cases that run different programs (a test runner and a command-line tool) keep separate captures. Each case runs with only `PATH` from the caller, `HOME` a scratch directory, `LC_ALL=C`, and `TZ=UTC`, so no token reaches the program and outputs do not depend on who captured them. `--parity` replays the same cases against the new program and exits 3 (a floor miss) on any compared stream that differs, naming the first differing line, and on a case with no golden output; without `--run` both only check the cases file. The person builds each program with its own toolchain; a modernisation Story's parity criterion is this command, so the result is deterministic (ground rule 7). Wiring parity into the merge gate as a feature-map check is left to the founder (`TestSurveyGoldenParity`)
