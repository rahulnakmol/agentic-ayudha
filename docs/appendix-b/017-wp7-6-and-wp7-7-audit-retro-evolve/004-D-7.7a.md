# D-7.7a

## Plan assumption

WP7.7 `evolve`: quarterly, accepted retro Feedback → first a failing eval case that reproduces it → a skill diff that passes → a PR labelled `agent-authored`, human CODEOWNER review, never auto-merged; ships via `rolling`; `install --pin` rollback; per-skill correction rate tracked before and after; accept: an `evolve` PR without a new eval case is rejected by CI

## Finding

Tier 1 checks recorded runs, not live skills, so "fails before, passes after" has to be two recorded runs. The plan does not say what marks a PR as an evolve PR, what "accepted" Feedback is, or which CI job rejects it. `internal/evals` replays CLI calls, so it imports `internal/cli` and the CLI cannot import it. A `pull_request` workflow re-runs on new commits, not on label changes, unless it lists those event types

## Implemented instead

An evolve case is an eval case with `feedback = <issue>` and `reproduce = "<dir>"` (new case keys): `<dir>` holds the current skill's recorded run (the `output/` artifacts under that name) and must fail tier 1; `output/` holds the new skill's run and must pass. `evals.EvolveGate` (the eval-first gate) requires, for the change against its base, at least one added `evals/cases/<skill>/<name>/case.toml` that names its Feedback and reproduce directory, a diff to that skill (`skills/<skill>/` or `evals/skills/<skill>/`), the old run existing and validating against its schemas yet failing another tier-1 check (a missing or malformed run reproduces nothing), and the new run passing tier 1. An evolve PR is one whose head branch starts `evolve/` or that has a commit carrying the `Aayudha-Evolve:` trailer; both change only with a push, which re-runs CI, whereas a label can be added without re-running the required check, so the `aayu:evolve` label is applied for people but never decides (CI fetches the PR's commits to read the trailers). CI: the required `build` job runs `go run ./internal/evals/cmd/eval -evolve-gate -base HEAD^1` on every PR (the merge commit's first parent is the base) and fails an evolve PR the gate refuses, so it cannot merge without a bypass; other PRs pass the step. `aayu evolve` without `--feedback` (the quarterly WP7.1 loop, now rendered for Amp, Cursor, and Actions) lists the open, accepted retro Feedback with the skill each names and writes nothing. `aayu evolve --skill <skill> --feedback <n>` acts only on an open Feedback issue filed by `aayu retro` (title prefix) and accepted: it carries `needs:grill`, triage's existing "accepted Feedback" label, and `evolve` takes it instead of `grill` when it is about a skill. The first run cuts `.aayudha/worktrees/evolve-<skill>-<n>` on `evolve/<skill>-<n>` (keyed by both, so another skill for the same Feedback gets its own worktree and branch) from `origin/dev`; the next runs the same gate (the binary injects it, `cli.Options.EvolveGate`, because of the import cycle), and on a pass commits with DCO sign-off and an `Aayudha-Evolve: #n` trailer, pushes with the verb's token, opens the PR (`Refs #n`, the cases, the rollback command), and labels it `agent-authored` and `aayu:evolve`. It never merges; `skills/` is a protected path, so a human CODEOWNER reviews it. On a refusal nothing is committed or written. The per-skill correction rate before and after is `retro`'s skills table (agent PRs that changed `skills/<skill>/`, and their WP5.7 corrections) in the retro windows on either side of the merge, so `evolve` does not compute its own. "Quarterly" is the WP7.1 loop schedule (day 2 of January, April, July, and October). Tests: `TestEvolveGateCI` (the CI entry point over a scratch git repository: an evolve PR with only a skill diff is rejected, and so is one marked only by an `Aayudha-Evolve:` commit; a case whose old run is missing is rejected; a case whose old run passes, or a case without a skill diff, is rejected; an eval-first PR passes; a non-evolve PR is not checked, whatever its labels) and `TestEvolveVerb` (the verb against the fake GitHub: listing, refusals of unaccepted, non-retro, or closed Feedback, a case for another Feedback, a binary without the gate, an eval-first PR opened once and never merged)
