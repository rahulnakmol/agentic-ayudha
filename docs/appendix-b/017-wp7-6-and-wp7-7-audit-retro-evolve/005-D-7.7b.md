# D-7.7b

## Plan assumption

WP7.7 CI gate, found on #138: the "Eval-first gate for evolve PRs" step failed intermittently with `git log HEAD^1..HEAD: exit status 128`; re-runs did not help, a fresh push did

## Finding

The step read the PR's commits from the checked-out test-merge commit (`HEAD^1..HEAD`, after `git fetch --deepen`). GitHub recomputes `refs/pull/<n>/merge` when the base moves, so a run's checked-out merge can stop being on any ref; deepening it then cannot fetch its parents, and a re-run checks out the same event's merge. `TestEvolveGateAfterTestMergeRecomputed` replays this against a local origin (shallow checkout of the merge, dev moves, the merge is recomputed and the old one pruned) and gets the same error from the old step

## Implemented instead

The step passes the event's `pull_request.base.sha` and `head.sha` (`eval -evolve-gate -base <sha> -head <sha>`), and the gate fetches whichever of them, or their merge base, the checkout lacks from origin by SHA (with history, so the merge base exists), never using the merge commit. The PR's commits are `base..head` (two dots: only the PR's own commits, so a base commit's `Aayudha-Evolve:` trailer cannot mark it); its change is `base...head` (three dots: from the merge base, so base commits made after the PR branched are not in it). The eval cases are still read from the checked-out tree. The same test checks that the gate passes an eval-first PR and refuses an evolve commit without a case in that replay
