# D-7.2b.3a

## Plan assumption

WP7.2b.3: `init --integrations` offers azure, aws, gcp with a cost/scope summary and `y/N`, writes `[integrations.<cloud>]`, prints and writes the least-privilege setup and the GitHub Actions OIDC federation under `.aayudha/setup/<cloud>/`; `doctor` verifies reachability and read-only scope, refusing write-capable credentials; a getting-started page per cloud through `tell docs --site`

## Finding

Creating the cloud identities needs the founder's cloud accounts, which init does not hold and the plan does not give it (V1: init is the human's, and cloud admin rights are not GitHub rights). The identifiers the config needs (tenant, role ARN, workload identity provider) exist only after those steps. A committed config serves both GitHub Actions and the founder's machine, which have different credentials

## Implemented instead

init writes the section with `auth = "oidc"` and empty identifiers (doctor names each missing one), plus `.aayudha/setup/<cloud>/`, rendered for the repository and its default branch from templates embedded in the binary (`initrepo.SetupFiles`), and prints the cloud's `README.md`: Azure `federated-credential.json` (subject `repo:<owner>/<name>:ref:refs/heads/<default branch>`), `lifecycle-policy.json` (the proof-media rule for a SAS-only container), and `az` steps assigning Monitoring Reader on the component and Log Analytics Reader on its workspace; AWS `trust-policy.json` (the GitHub OIDC provider, audience `sts.amazonaws.com`, the same subject), `read-policy.json` (`logs:StartQuery` on the RUM log group, `logs:GetQueryResults`, `rum:GetAppMonitor` and `rum:GetAppMonitorData` on the monitor, and `iam:SimulatePrincipalPolicy` on the role itself), and `media-policy.json`; GCP `gcloud`/`bq` steps for `roles/bigquery.dataViewer` on the dataset, `roles/bigquery.jobUser`, a workload identity pool and provider whose attribute condition admits only the repository and branch, and `roles/iam.workloadIdentityUser`; every cloud a `workflow.yml` with `id-token: write`. Existing setup files are kept on a rerun, so init stays idempotent. Locally the founder overrides auth for one run (`AAYU_INTEGRATIONS__<CLOUD>__AUTH=cli`); the CLI login must itself be read-only (GCP impersonates the service account; AWS uses a profile that assumes the role; an Azure Owner login is refused). doctor needs no new check: its integrations row lists the three adapters and reports the WP7.2b.1 scope checks. Pages: `docs/getting-started-azure.md`, `-aws.md`, `-gcp.md` in a new "Clouds" sidebar group, each with the founder actions; `docs/getting-started.md` links them. Tests: `TestInitExtras` (golden setup files under `internal/cli/testdata/setup/`, JSON validity, printed steps, the config validating, idempotent rerun, `uninit --external` listing the three integrations). Founder actions (none can be done from here; no cloud account exists): Azure, an app registration with the federated credential and the two reader roles, plus optionally a storage account with a private container and a SAS token or an Entra identity with Storage Blob Data Contributor; AWS, the GitHub OIDC provider, the role with the trust and read policies, the app monitor's CloudWatch Logs copy, plus optionally an S3 bucket and an IAM user with the media policy; GCP, the read-only service account with its two roles, the workload identity pool and provider with the binding, plus optionally a bucket with public access prevention and a media service account; then fill each section's identifiers and add `id-token: write` to the jobs that run `aayu`
