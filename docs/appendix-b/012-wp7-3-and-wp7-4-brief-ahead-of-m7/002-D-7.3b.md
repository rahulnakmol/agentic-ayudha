# D-7.3b

## Plan assumption

WP7.3 accept: register evals, tier 2 at the WP3.4 bar per register, the `eli5` rubric additionally requiring a reading grade of at most 6 and `ste` the STE lint

## Finding

WP3.4's tier 2 drafts JSON work items, scores the suite as a whole, and has no step for the host's loop of rendering, reading `aayu brief`'s findings, and revising. The STE word list is a reference the host reads, not part of the skill body. Whether a grade or a lint passed is decidable, so it should not be left to the judge (rule 7)

## Implemented instead

Four cases on one grounding (`evals/cases/brief/grounding.json`: Feature #7 with Story #12, its authoritative pack P1, and a Result): `eli5-explain`, `ste-explain`, `engineer-ideate`, `regulatory-close`. A new case key `brief = { register, purpose, draft }`: tier 1 runs the same checks on the recorded draft and renders it (alt text). Tier 2: the skill model is `brief`'s registry lane (`spec`: `claude-opus-5-5`, fallback `claude-sonnet-5-5`), the judge stays `gpt-6.1-sol`, k = 5; the prompt is the skill body plus the case's `[tier2] references` (`ste-words.md` for `ste`) with the grounding as an untrusted block, and the reply is the Markdown draft. A draft that fails the checks gets the findings once and revises, as the skill's step 3 does in a host; one that still fails scores 1 without the judge (`revised` marks runs that needed the revision). So grade ≤ 6 and the STE lint are deterministic preconditions of a score, and the judge is told which checks passed. `Compare` applies the bar (pass^k ≥ 0.8, mean ≥ 3.5) to every case as well as the suite, which is the per-register bar (for the single stub case nothing changes). `max_usd` 3.0 → 9.0 for twenty more runs. `evals.yml`'s dev-push filter adds `internal/brief/`. `TestTier2BriefRevisesOnceThenJudges` covers the revision, the floor score, and the per-case bar. The first live run, evals.yml run 38200697472 on 41a8a56 (charged 6.21 USD), failed. The stub held (pass^5 1, mean 5.00), but every brief case had pass^5 0: eli5 mean 2.80, engineer-ideate 4.40, regulatory-close 3.80, and ste-explain 2.67 with 2 errors. No draft failed the deterministic checks. The judges scored 3 for a changed fact: a rate per reviewer given as "each reviewer" or with "per reviewer" dropped, a button or a save action no source names, "merged" for "released", "not tested" for "out of scope". In `ste`, the lint rejected "reviewer" (not in the titles), so drafts wrote "users" and changed the metric. Two `ste` drafts spent the 4000-token cap on thinking. Fix (one round, as the founder asked): the skill's Draft rules now keep every number's unit and population, record states only as the sources do, and name no screen detail, reason, or effect that no source names; the words of the subject's summary and of the Result are technical names too; the skill cap is 8000 and `max_usd` 12.0. The verification run, evals.yml run 38202244333 on fec95a5 (charged 7.35 USD), still failed. Nothing errored and the stub held at 5.00. The brief cases still had pass^5 0: eli5 mean 3.80, engineer-ideate 3.40, regulatory-close 4.20, ste-explain 3.60. The remaining defect is in the grounding, not the drafts. `brief.Pack` lists a pack's artifacts but not its `criteria` map (criterion → evidence), so a draft that says "the recording proves criterion 3" makes a claim the judge cannot trace, and every case was marked down for it. Open (founder decision, no further fix round taken): add each pack's criterion → evidence map, and once WP4.8 posts it, the inspect disposition per criterion, to the grounding; or have the skill state criteria only as the expected results the evidence is mapped to
